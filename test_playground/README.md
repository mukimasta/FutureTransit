# FutureTransit 最小调度原型

这是一个可重复的离散时间实验：10 栋楼、30 辆可复用 Pod、5 个支线节点、5 个主干 merge/split 节点。Python 标准库实现，使用 uv 创建环境，无第三方依赖。

## 运行

```sh
cd /Users/mukii/Projects/FutureTransit/test_playground
uv run python simulator.py
open results/demo/replay.html
uv run python -m unittest -v
uv run python benchmark.py
```

回放文件自带全部数据，可直接双击打开，无需服务器或网络。播放/暂停、倍速、时间拖动、车辆选择及路线高亮用于追踪具体 Pod。页面上方是整场汇总，右侧是当前时刻状态。根目录的 `replay.html` 是生成模板，请打开 `results/demo/replay.html`。

连续运行同一批 30 辆车，每车完成 20 次行程：

```sh
uv run python simulator.py --scenario bottleneck --rounds 20 --seed 7 --output results/custom
open results/custom/replay.html
```

`--scenario` 可选 random（随机目的楼宇）、bottleneck（汇入 B00，随后离开）、opposing（B00/B06 两端对冲）、cycle（目的楼宇编号轮转）。`--fleet` 设置实际车辆数，`--rounds` 设置每车行程数，`--clearance` 设置资源释放后的保护秒数，默认 1 秒。

## 调度规则

1. **分层路径**：楼宇 B → 支线 S → 主干 J；只在主干子图使用 Dijkstra；再沿目的地支线进入楼宇。同一支线的两栋楼直接经 S 通行。
2. **资源互斥**：所有边都是单线双向，同向和反向车辆共用一个区间资源。每个 S/J 节点是一个完整冲突区，任意转向均互斥；楼宇各有一个共用进出泊位。
3. **时间预约**：整数秒，物理占用采用半开区间 `[start, end)`，另保留 1 秒释放保护。楼宇泊位停留 2 秒，S/J 节点停留 1 秒，楼宇接入边 4 秒、支线边 5 秒、主干环边 8 秒、主干捷径 10 秒。时间是实验参数，不对应真实速度或距离。
4. **整程原子提交**：按请求时刻、Pod 编号依次处理。先检查完整轨迹，任一资源有冲突，就将出发时刻向后移动并重新检查；只有整条行程可行才写入预约表。不同资源允许多车同时运行。
5. **车辆连续性**：抵达后进入楼宇内部停车区，3 秒后才生成下一次请求。下一程起点严格等于上一程终点。内部等待/停车空间暂设无限，和进出泊位分开。

## 为什么这个模型不会形成循环等待

未获完整预约的 Pod 不占用轨道或进出泊位；出发后整段路径都有已确定的通行窗口，途中不申请新资源，也不停车等别人。因此，在准时执行假设下，不存在“占着 A 等 B、占着 B 等 A”的循环等待。

对于每次请求，已有预约有限；最迟可以在所有已有预约结束后串行完成这条路径。搜索每次碰撞都严格增加出发时刻，因此有限请求必定得到有限时刻的安排。未来请求不能修改已批准行程。

这是**这个模型内的性质**。回放按计划精确执行，没有对延误或故障的容错保证。`unfinished_trips=0` 记录所有行程到达；它不代表在任意真实网络上证明了无死锁。

## 验证和输出

每次运行生成：

- `run.json`：节点、轨道、每车分段轨迹和指标。
- `trips.csv`：起终点、请求/出发/到达时刻、等待及完整路径。
- `events.log`：按时间排序的请求、出发、进入各条边、抵达日志。
- `metrics.json`：机器可读统计。
- `replay.html`：离线交互回放。

验证器不读取预约表，直接从轨迹逐秒重建节点和无向区间占用，检查物理冲突、保护间隔、连接连续性、耗时、车辆复用和终点。11 个测试覆盖全部 90 对起终点、资源边界、故意注入的同向/反向冲突、错误车辆位置、无残留部分预约、并行通行、50 个随机种子和 4 类连续运行场景。

吞吐量 = 完成行程数 / 从 0 秒到最后抵达的模拟时间；这是整场平均，包含启动和收尾。等待时间 = 出发 − 请求；P95 为最近秩法。`scheduling_ms` 是实际规划耗时，不含轨迹审计、文件生成或浏览器显示，随机器/运行波动。

## 下一步

这条路线值得继续扩展为游戏调度底座，但当前策略在双向对冲下效率很低。优先比较单向双轨、方向分批放行或拥堵感知的候选路径；然后加入有限楼宇停车位/接入缓冲与预约准入；再做延误触发的安全重调度。动态编组和数千车规模尚未验证。

当前连续运行是固定 30 辆车的闭环负载，会因等待自动降低请求频率；它不能证明外部需求持续涌入时队列稳定。还没有乘客派单、车辆加减速/长度、真实制动距离、途中故障、线路变更或网络缓存清理。地图是拓扑示意，不能用图上两个圆点的几何间距推断真实安全距离。

实测数据见 `RESULTS.md` 和 `results/benchmark.json`。
