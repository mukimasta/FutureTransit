# 双向共享车道 / Bidirectionally shared lanes

## 规则

`Track.lanes` 为 `1 | 2 | 3`，缺省仍按旧版单车道处理。每条物理车道完全相同，没有固定行驶方向：任一时刻一条车道只能由一辆 Pod 占用，但同一轨道单元的不同车道可让同向或反向 Pod 并行通过。

资源键使用物理边的规范方向，而不是 Pod 朝向：

- 单车道：`edge:<canonical-edge>`
- 多车道：`lane:<canonical-edge>:<0..2>`
- 直通的同容量二度节点：`node-lane:<point>:<lane-index>`
- 汇入、分岔、容量变化与泊位接点：共享 `node:<point>`

因此，Pod 改变行驶方向不会改变某条物理车道的身份。渲染偏移也只由规范边方向和已选 lane index 决定。

## 调度

调度器为每条候选路线有界尝试 profile `0..2`。profile 在每个物理单元映射到该单元存在的最高合法车道，重复 profile 会被去重。所有候选按最早可出发时间、最早到达时间和最早结束时间选择，因此繁忙的 0 号车道不会掩盖空闲的 1/2 号车道。

同一 profile 贯穿连续的同容量走廊。只有严格的二度、同容量走廊允许按车道通过节点；真实汇入和分岔继续共享节点资源，不能借不同 profile 绕过冲突。

## 路段安全缓冲

新计划写入 `ServicePlan.safetyBuffer: 1`。Pod 行驶在一个 move 路段时，会同时预约实际路线中紧邻的前一段、当前段和后一段，形成一段前后各一个物理单元的空间冗余：

- 只预约相邻 move 已选择的那条物理车道及其必要 crossing 资源，不锁同边的其它平行车道。
- 不推测或预约岔路上的未行驶分支。
- `boarding`、`alighting` 或显式 `node` 段会截断缓冲，不跨停站继续占用另一侧轨道。
- 缓冲窗口按连续运动合并，Pod 不会因此在每个网格点停车；附加窗口不会超过该持久计划最后一个 segment 的结束时间。

旧在途计划没有 `safetyBuffer`，加载时按 `0` 处理并使用旧预约间距完成，避免扩张既有预约后制造读档冲突。所有新调度、提交校验、存档重建和旧方向资源迁移都显式使用计划自身的同一缓冲值。

## 对角交叉

每个对角线车道占用一个固定的 3×3 行/列资源集合。同一条对角线的不同车道集合互不重叠；另一条对角线的任意车道都会与它共享恰好一个资源。这样同一物理边的不同车道可并行，但两条相交对角线始终互斥。

## 升级与存档

`upgrade-tracks` 的 `lanes?: 2 | 3` 和待办的 `targetLanes?: 2 | 3` 缺省均表示旧版目标 2。增量费用为：

`10 × 单元长度 × (目标车道数 - 当前车道数)`

加载旧 v1 活跃计划时，旧的有向双轨资源按物理边规范方向安全映射到共享 0/1 号车道，并重建预约日历；计划、Pod 和乘客状态不会被删除。导入仍会独立重建轨迹需求，并拒绝不存在的车道编号、缺失预约或冲突预约。

## 模块边界

- `network`：合法车道资源、连续走廊节点与对角交叉资源。
- `scheduler`：profile 搜索、最早时刻选择与原子提交。
- `shared/trajectory`：从几何、时刻和合法车道选择重建预约。
- `persistence`：旧资源兼容、三车道与增量升级账本验证。
- `shared/selectors`：依据物理 lane index 计算 Pod 显示偏移。
