# 容量验收 / Capacity acceptance

容量由真实轨迹段、节点、泊位和最终停车尾部共同决定；额外 Pod 本身不会创造轨道或站台容量。单线/单站台会产生 `track-busy` 等可见等待原因，独立线路和双车道可提高并发准入，但路口仍需协调。当前调度可能过于保守地拒绝同时请求，不能描述为成熟排队吞吐系统。

生产有效的容量夹具覆盖 8 个同时请求的基线与扩容比较，另有固定四轮开发后、30 辆已连接 Pod、31 个专用停车位的 3,600 模拟秒运行。持续增长没有完成条件，因此负载夹具不能再循环等待 `growth.complete`；人口也不能写死为旧版 156。旧固定方向车道版本的吞吐与耗时不再作为当前结果；共享车道、安全缓冲和停车规则变化后需要重新校准。注入 100,000 预算只是性能夹具，不是经济平衡或可玩性证明。

容量测试独立重建 `MotionSegment.resources` 和终点承诺，不把预约表无重叠当作充分证明。预算测试是逐项包络，不是完整游玩流程。30 分钟人类试玩、双车道/流量图层的浏览器验收仍以 [VALIDATION.md](../VALIDATION.md) 的状态为准。
