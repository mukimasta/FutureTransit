## 2. 原来为何不会循环等待

旧模型只在完整轨迹都可用后写入预约，未批准的车辆在楼内等待，不占任何轨道和进出泊位。车辆出发后不再申请额外资源，按计划精确执行。

在这些假设下，不会形成途中「占着 A 等 B、占着 B 等 A」。既有预约有限时，总能把下一趟排到它们全部结束之后。

关键限制：

- 楼宇内部停车无限，抵达车辆在短暂泊位操作后进入不占道路的内部空间。
- 请求由 Pod 自己的上一趟完成触发，没有独立于车队的真实居民需求。
- 路径假定固定 B/S/J 层级，不是玩家任意画出的几何网络。
- 没有居民派单、有限停车、途中延误、运行中拆轨或动态编组。

新版继承原子预约思想、资源互斥语义与独立审计方法；固定地图、假乘客来源与无限停车不能继承。

## 3. 最先解决有限停车

最小反例：A、B 各一个泊位，都停着一辆车，互相有出行需求。若两车都必须先取得目的泊位再出发，就可能谁也不能动；只检查轨道冲突无法解决。

建议建立以下模型，再通过小规模穷举和模拟确认：

1. 平台和停车位均为真实有限终点资源，停泊占用持续到确定离开，不在下客动画结束时自动释放。
2. 停泊资源位于通行网络旁，不能充当其他车辆的必经通道；节点冲突区不用于无限停车。
3. 每次服务一次性安排空车接近、上下客、载客行驶及最终停泊位置；必要时包含下客后撤至停车位的空驶。
4. 最终泊位从预计到达起持续占用，直到这辆车后续离开的计划提交；不能被第二辆车重复承诺。
5. 新计划提交时，旧泊位的释放、全部通行预约、新泊位的占用一起修改。失败则一个也不修改。

建议将「每个运营连通分量至少有 Pod 数量 + 1 个可停泊位置」作为首版保守的容量准入规则。平台也算位置；检查的是停车承诺，不只是屏幕上此刻有几个空格。

保留一个可调度的空位，可供占着目的平台的空闲 Pod 搬移。搬移同样要完整预约，完成后再安排受影响的服务。下单买车、拆停车位、断开路网都需重新检查。

**额外空位本身不是任意网络无死锁的证明。** 这一方案依赖停泊不阻断通路、泊位真实可达、终点不重复承诺、既有行程有限且准时完成，以及搬移公平性。后续测试若不能支持它，应调整准入或预约策略，不能用隐藏停车补洞。

有无限期泊位占用时，旧代码的无限向后搜索不能照搬。必须先判断容量阻塞、尝试合法搬移；超过规划窗口仍不可行时返回可解释的待服务状态，等资源变化再评估。

## 4. 派单、寻路、预约分开

三个模块回答不同问题：

- 派单：哪辆空闲 Pod 服务哪个具体居民，使用哪两个平台。
- 寻路：它从真实所在泊位去接客、送达和停泊有哪些可行路径。
- 预约：这些动作在什么时间可以不冲突地执行。

首版建议按请求等待时长处理，稳定 ID 打破同序。优先评估少量可行车辆，以预计接客与送达时间比较，不用直线距离代替路网耗时。

路线在玩家通行图上寻找，平台和停车位只能作为本段起终点。先用有确定结果的最短路，保留少量替代路径的接口；是否需要候选绕路由相同需求下的对冲/交叉测试决定。

评估各候选的预约必须只读。最终胜出的方案才原子提交，未中选方案不能提前占住资源。公平性记录在请求层，避免较难服务的居民永远被新请求插队。

已批准的行程不被后来请求抢占。开放需求超过容量时，不承诺每个请求立即或无限期最终得到 Pod；可显示等待、拒绝报价或让未派车居民选择步行。已承诺行程能完成与需求队列稳定是不同指标。

## 5. 时间、占用与实体一致性

- 模拟使用确定步长或事件时间，渲染只在已确定状态之间插值，不由动画结束事件释放资源。
- 资源窗口沿用半开区间和明确的清空间隔；Pod 在节点及区间之间的交接要按完整时间模板执行。
- 每个人只能处于一个位置：建筑、步行路径、平台队列或某辆 Pod。建筑名单、乘客图标和人数统计从同一位置数据推导。
- 每辆 Pod 只能处于一个泊位、区间或节点，同一时间最多承载一人且最多服务一个订单。
- 行程记下请求、到队列、空车出发、上车、载客出发、下车、抵达建筑时刻；区分空驶、乘坐与候车时间。
- ETA 必须包含实际预约与完整接送过程；暂时不可安排的请求不伪造确定到达时间。
- 保存/恢复若加入首版，须保存模拟时间、居民状态、随机数状态、车辆、订单与完整已承诺计划，不能只保存地图后重新生成乘客。

## 6. 动态编辑

轨道几何编译成带稳定资源 ID 的通行图。控制点变化不能在车辆仍占用时悄悄改变区间边界。

建议流程：编辑草稿，标出受影响资源，停止其新预约，让所有涉及这些资源的已承诺动作完成，在模拟边界提交拓扑变化、重建寻路信息并结算净费用。

涉及终点停泊位置的拆除，需先安排车辆搬移和替代落位。若无法排空或会让容量条件失效，草稿明确显示原因并保持未提交，不删除实体。暂停期间完成设计，恢复后执行排空。

## 7. 模块职责建议

Web 实现建议使用 TypeScript 和独立模拟线程；渲染库在交互样本验证后决定。沿用模块隔离原则，不自动搬回旧 UI 或旧模拟代码。

| 模块 | 所有权与职责 | 不应承担 |
| --- | --- | --- |
| 世界与居民 | 建筑、人口、活动、真实目的地、种子随机 | 生成伪造的载客车辆 |
| 交通选择 | 步行寻路、方式比较、交通请求 | 正式写入车辆预约 |
| 路网 | 网格几何、固定区间、交叉冲突、平台连接 | 根据画面推断占用 |
| 派单与预约 | 车辆分配、路线评估、泊位承诺、原子提交 | 直接操作 UI 或图形对象 |
| 模拟运行 | 唯一时间推进、实体状态迁移、守恒审计 | 用动画帧控制逻辑 |
| 城市与经济 | 增长事件、建设账本、票款、补助 | 用现金不足停止已承诺行程 |
| 交互与呈现 | 命令、草稿、选择/追踪、地图和面板 | 私自修改居民与车辆状态 |

共享协议只传实体 ID、命令、快照和事件。展示多个逻辑模块不意味着每个模块都需要一个线程；首版一个模拟线程即可作为设计起点。

## 8. 实施顺序与验收门槛

1. 建立新调度底座：保留旧实验作为对照，先验证通用图、有限泊位、真实车辆复用、原子失败不留预约。展示最小轨迹回放用于核对。
2. 三栋楼的完整接送：24 个持久居民能步行、选方式、排队；4 辆车真实空驶和送达；所有人、车和平台可点击关联。先让第一人接送成立。
3. 自由建设与容量玩法：平台/停车、斜线和圆角、交叉冲突、暂停改造、泊位搬移。能通过具体改造改善具体问题。
4. 城市成长与预算：扩大到 100～200 人及 20～30 辆车，加入工作/常去地点变化、补助和建造成本，再校准 30 分钟节奏。

每一步在运行中的画面和独立审计中验收。居民与接送没有成立之前，不推进完整 HUD、复杂美术和装饰性增长。

关键新增验证用例：

- 两个满平台互换，以及增加第三泊位后的合法搬移和服务。
- 多辆空车竞争同一个接客平台、终点平台和停车位，确保不重复承诺。
- 送达平台短时可用、送达后无停车位：只能拒绝或安排完整撤离，不能卡在途中。
- 单线双向对冲、环路、平面交叉及斜线中点相交；独立轨道仍可并行。
- 原子候选评估和失败回滚不改变其他车辆计划；长等请求的公平性可观察。
- 独立居民持续产生需求的过载场景，区分安全性、服务率、最大等待和转步行比例。
- 行驶中拆改、分裂连通分量、暂停/加速，保护实体连续性和已承诺计划。
- 居民守恒、车辆守恒、停泊和轨道占用守恒、收入单次结算。

性能在目标浏览器以 200 居民、30 辆 Pod 及最长试玩持续时间测量，记录模拟耗时、交互延迟和过期预约回收；旧 Python 小地图结果不能代替这项验收。
