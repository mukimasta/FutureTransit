# 交互和玩法准则

## 来自试玩的核心修正

1. **游戏画面不是运营后台。** 地图占据整个窗口，常驻控件只保留当前行动和少量结果；经营明细、存档、帮助收进按需打开的面板。
2. **楼宇先于交通设施存在。** 城市没有预摆的客运站点。所有画出的建筑都是真实可接入建筑，用户选择楼宇端口的方向，再自己建设入口。
3. **玩家建设轨道网络。** 可以在地图空地铺设连续轨道、创建分合流节点和接入已有网络，而不是在预置目的地间选择连线。
4. **建筑不充当中转站。** 楼宇是出发/到达端点；穿行、汇入、分流发生在玩家建造的轨道节点。乘客始终乘同一辆 Pod。
5. **空间上的动作要有即时反馈。** 预览路线、吸附对象、施工费用和不可行原因；结束/取消建设是明显操作。新增功能不能只靠隐藏命令存在。

当前绘轨操作：切到“绘轨”后，点击已建接入口、枢纽、既有轨道或空地添加点；点击建筑端点会提交整条线路。空地线路可按 Enter 或点击确认提交，Esc 取消，Backspace 删除最后一个点。草稿不修改资金或网络，直到 `drawTrack` 事务成功。

## 参考及取舍

参考官方的 [Mini Metro 介绍与画面](https://dinopoloclub.com/press/mini-metro/) 和 [Mini Motorways 介绍与画面](https://dinopoloclub.com/press/mini-motorways/)。它们强调直接在地图上设计网络、应对城市变化并管理有限升级；本项目借鉴信息层级、直接操纵和留白，不复制它们的站点分类、固定线路或失败机制。

应用到 Future Transit：暖纸色城市底图、清晰且流动的轨道、少量圆形/胶囊控件、短任务提示、选中对象才出现的操作卡。中文和英文都要保持同样的简洁程度。

## 模块细分

| 工作包 | 边界 |
|---|---|
| 网络编辑 | 轨道几何、吸附、分岔、拆除和施工事务 |
| 预约与车辆执行 | 路由、原子预约、保护间隔、连续轨迹 |
| 城市需求 | 固定种子 OD、旧交通选择、候车和放弃 |
| 经营与事件 | 造价、票价、车辆成本、任务奖励、活动压力 |
| 地图美术 | 可接入建筑、地形、层级、相机和车辆表现 |
| 游戏界面 | 简洁工具、对象操作、中英双语、教程 |
| 独立验收 | 轨迹审计、编辑事务、存档、真实浏览器试玩 |

按接口稳定程度分批并行，主代理统一依赖方向与最终验收。文档写当前行为和已知限制，不能把计划功能写成已实现。
